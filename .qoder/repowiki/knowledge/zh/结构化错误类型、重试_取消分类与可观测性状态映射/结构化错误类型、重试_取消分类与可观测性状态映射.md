## 1. 整体方案

本仓库采用「自定义 Error 子类 + 稳定 code 字符串 + 统一分类器」的模式处理错误：
- 所有业务错误均继承 `Error`，并附带一个稳定的 `code` 字段（如 `'LLM_CALL_TIMEOUT'`、`'UNSUPPORTED_SCHEMA_VERSION'`），便于调用方按码分支处理。
- 在 `packages/core/src/errors.ts` 集中定义框架级错误类，并提供 `isRetryableError` / `isCancellationError` 两个纯函数对任意 `unknown` 错误进行重试/取消判定。
- 可观测层通过 `packages/core/src/observability/status.ts` 的 `classifyRunFailure` 把运行时异常转换为 JSON 安全的 `RunStatus` + `StructuredTraceError`，自动提取 `code`、`name`、`httpStatus`、`retryable` 等字段。
- CLI 层使用独立的 `DashboardCliError` / `OmaValidationError` 配合 `EXIT` 常量（`SUCCESS`/`RUN_FAILED`/`USAGE`/`INTERNAL`）控制进程退出码。
- 存储子系统（EvalStore、TraceStore、FileTraceStore、DurableApproval）各自定义 `*ErrorCode` 联合类型及对应 `*Error` 类，用于区分参数校验失败、schema 版本不兼容、文件损坏等底层故障。

该模式贯穿 agent、orchestrator、eval、observability、cli 各子模块，形成统一的“抛错 → 分类 → 记录/上报”链路。
